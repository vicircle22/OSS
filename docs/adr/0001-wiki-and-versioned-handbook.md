# ADR-0001: Wiki와 저장소 문서 사본으로 협업 지식 보존

- 상태: **이번 과제에서 적용 / 팀의 장기 운영 합의는 미기록**
- 적용일: 2026-11-04
- 작성: XAplus 계정의 AI 보조 작업
- 근거: 5주차 과제의 Wiki 3문서·상호 링크 요구
- 관련 제안: [RFC-0001](../rfc/0001-async-response-policy.md)

## 배경

현재 저장소에는 PRD·와이어프레임·DORA·협업 안내가 있으나 새 구성원이 읽을 Wiki가 없었습니다.
반복 질문의 답을 검색 가능하게 만들고, Wiki가 별도 Git 저장소라는 점을 고려해 검토·복구 가능한 사본이 필요합니다.

## 대안

| 대안 | 장점 | 비용·한계 |
|---|---|---|
| Wiki만 유지 | 바로 편집·탐색 | 코드 PR과 변경을 같이 검토하기 어려움 |
| 저장소 docs만 유지 | 코드와 같은 이력 | 과제의 실제 Wiki 게시 요구를 만족하지 못함 |
| Wiki 게시 + docs/wiki 사본 | 실제 Wiki 탐색과 코드 저장소 검토·복구 근거 | 두 저장소 내용이 어긋날 수 있어 동기화 확인 필요 |

## 이번 적용

세 번째 방식을 사용합니다. Home과 Getting Started·Development Guide·Troubleshooting을 게시하고,
세 문서를 서로 연결합니다. 사이드바·푸터로 탐색을 보완합니다. 동일 Markdown을 `docs/wiki/`에 보존합니다.

일반 저장소의 커밋은 Wiki 게시를 대신하지 않습니다. 양쪽 변경과 게시 확인을 기록합니다.
이는 과제 실행의 결정이며 다른 팀원의 동의·수락 리뷰를 받았다고 주장하지 않습니다.

## 동기화 규칙 제안

1. Wiki를 먼저 fetch하고 실제 수정 내용을 확인합니다. 다른 사람의 편집을 무조건 덮어쓰지 않습니다.
2. 안내 변경은 docs/wiki 사본과 Wiki Git 양쪽에 반영하고 각 커밋을 기록합니다.
3. 충돌하면 현재 코드·원래 편집 의도를 확인해 합칩니다. 오래된 사본을 강제 push하지 않습니다.
4. 자동 양방향 동기화는 이번 범위에 넣지 않습니다. 필요하면 별도 ADR로 설계합니다.

## 검증과 복구

- 브라우저에서 세 페이지가 실제로 열리고 서로의 링크가 존재하는지 확인합니다.
- 문서의 로컬 서버·테스트·예시 생성 명령을 실행합니다.
- 두 저장소의 사본을 바이트 단위로 대조합니다.
- 잘못된 변경은 해당 저장소에서 되돌리는 커밋으로 처리합니다. 공개 이력 강제 재작성은 하지 않습니다.

## 후속 합의

유지 담당자·문서 갱신 주기·24시간 응답 목표·Discussions 운영은 RFC에서 별도 논의합니다.
