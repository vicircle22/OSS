# RFC-0001: 비동기 응답 정책과 Wiki·ADR 역할

- 상태: **토론 게시 전 초안 / 팀 합의 아님**
- 제안일: 2026-11-04
- 게시 대상: GitHub Discussions의 RFCs 카테고리 (활성화·권한 확보 후)
- 관련: [Wiki](https://github.com/vicircle22/OSS/wiki), [ADR-0001](../adr/0001-wiki-and-versioned-handbook.md), [자동화 초안](../automation/README.md)

## 문제

질문·실행 작업·기술 결정이 여러 곳에 흩어지면 같은 설명을 반복하고,
봇의 접수 안내만 남아도 사람이 응답했다고 착각할 수 있습니다.

## 제안

1. Wiki는 시작·개발·문제 해결의 반복 지식을, ADR은 오래 영향을 주는 결정 배경을 보존합니다.
2. 일반 질문은 Q&A, 기술 선택 제안은 RFCs에서 논의하고, 실행할 작업은 Issue·코드 변경은 PR로 연결합니다.
3. 일반 Issue의 첫 타인 응답 목표를 24시간 경과 시간으로 시범 제안합니다. 주말·휴가·시험 기간의 예외는 합의 후 조정합니다.
4. 작성자·Bot·[bot] 계정의 자동 접수는 응답 완료로 세지 않습니다.
5. 주간 보고서는 최근 7일 생성·종료·대기·응답 목표 초과를 읽기 전용으로 정리합니다. 자동 독촉은 하지 않습니다.
6. 자동 접수는 초안을 검토하고 별도 활성화 변수에 합의한 뒤 사용합니다.

## 대안과 비용

- SLA 없이 필요할 때만 확인: 운영 부담은 작지만 오래된 질문이 남기 쉽습니다.
- 24시간 경과 시간: 구현·해석이 단순하지만 주말·학사 일정을 반영하지 못합니다.
- 업무시간 달력 기준: 실제 생활과 맞추기 쉽지만 시간대·휴가·담당자 운영이 추가로 필요합니다.

## 토론할 질문

- 24시간 경과 시간 대신 평일 업무시간 기준이 필요한가요?
- 일반 Issue 외 PR 리뷰·Discussions도 추적할까요? 각각 다른 목표가 필요한가요?
- Wiki 사본 갱신 담당과 검토 주기를 어떻게 나눌까요?
- 봇 자동 접수는 필요한가요, 보고서만으로 충분한가요?

## 수락 조건

실제 팀원의 의견·선택한 대안·운영 범위를 기록하고 ADR 상태를 갱신합니다.
이 초안에는 아직 다른 사람의 답변·동의·투표·승인을 기록하지 않았습니다.

## Discussions 카테고리 설계

| 카테고리 | 형식 | 용도 |
|---|---|---|
| Announcements | Announcement | 운영 공지·문서 갱신 안내 |
| Q&A | Question / answer | 설치·실행·사용 질문과 해결 답변 |
| RFCs | Open-ended discussion | 배경·대안·영향·열린 질문을 가진 기술 제안 |

실제 설정 메뉴에 접근 권한이 없는 경우 소유자에게 활성화를 요청하고, 설계와 실제 게시 상태를 구별합니다.
