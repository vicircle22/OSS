# AI SUMMIT 코드 리뷰 가이드

목표: 버그 발견, 코드 품질 향상, 지식 공유, 일관성 유지, 함께 성장하는 팀 문화.

## 작성자

1. 한 PR에서 하나의 목적을 다룬다. 100~200줄은 권장 가이드이며 기계적인 제한이 아니다.
2. 제목은 `feat: 검색 추가`, `fix(api): 빈 입력 오류 수정`처럼 종류·대상·목적을 쓴다.
3. 문제, 바뀐 동작, 관련 Issue, 실행한 테스트와 결과, 한계를 PR 본문에 남긴다.
4. 초안은 Draft로 열고, 검토 가능해지면 작성자 외 팀원에게 리뷰를 요청한다.
5. 질문에는 배경과 근거로 답하고, 필수 지적 수정 후 커밋과 검증 결과를 연결한다.

## 리뷰어의 세 역할

1. **체계적으로 확인:** 기능·경계값·예외 처리·테스트·성능·보안·가독성·문서 일치.
2. **건설적으로 설명:** 사람을 평가하지 않고 코드 위치·문제·영향·가능한 대안을 제시.
3. **태그로 구분:** 필수 수정과 권장 개선, 사소한 의견을 구별.

| 태그 | 의미 | 예 |
|---|---|---|
| `[MUST]` | 병합 전 해결해야 할 결함·필수 조건 | 빈 입력에서 예외가 발생합니다. 검증과 회귀 테스트를 추가해 주세요. |
| `[SHOULD]` | 권장 개선. 미반영 시 이유를 합의 | 중복된 파싱 로직을 한 함수로 모으면 유지보수가 쉬워집니다. |
| `[NITS]` | 사소한 표현·취향 | 같은 뜻의 변수 이름을 문서와 맞추면 읽기 편합니다. |

문제 없이 확인한 항목은 `[MUST][확인 완료]`처럼 **상태를 명시**한다.
실제 결함이 없는데 수정 요청을 만들거나, 단순 확인을 미해결 결함처럼 표현하지 않는다.

## 피드백과 반영 흐름

1. Files changed에서 변경 줄을 읽고 필요하면 로컬에서 재현한다.
2. 태그·근거·영향·개선안을 넣어 Review를 제출한다. 미해결 결함은 Request changes,
   설명·자체 점검은 Comment, 작성자 외 리뷰어의 수락은 Approve로 구분한다.
3. 작성자는 수정 커밋과 재현/테스트 결과로 답한다. 의견이 다르면 근거로 토론한다.
4. 리뷰어가 최신 커밋을 확인한 뒤 대화를 해결한다. 작성자가 대화를 닫은 사실만으로 수락으로 간주하지 않는다.
5. 필수 지적 해결·검증·동료 승인을 확인한 후 병합한다. 새로운 변경이면 재검토한다.

좋은 피드백 예:

> [MUST] 실패 배포 수를 성공 배포 수로 나누고 있어 비율이 잘못됩니다.
> 분모를 전체 배포 수로 바꾸고 10회 중 2회 실패 → 20% 테스트를 추가해 주세요.

피할 표현: “코드가 끔찍하다”, “다시 하라”처럼 위치·이유·대안이 없는 비난.

## 실습 증거와 역할 구분

- 최소 **서로 다른 PR 3개**를 실제로 검토하고 PR/Review 링크·검토 SHA·태그·후속 조치를 기록한다.
- 같은 PR에 코멘트 세 개를 썼다고 PR 세 건을 리뷰했다고 세지 않는다.
- 예시, 작성자 자체 점검, AI 보조 점검, 다른 팀원의 독립 리뷰를 구별한다.
- AI가 작성자 계정에서 남긴 Comment는 동료가 읽고 승인했다는 증거가 아니다.
- 발견하지 않은 결함, 실행하지 않은 테스트, 존재하지 않는 승인·피드백 반영을 기록하지 않는다.
- 제출할 때는 수업의 ‘3건’이 팀 합계인지 개인별인지 확인한다. 이 문서는 개인별 충족을 단정하지 않는다.

## 병합 전 체크

- [ ] 최신 변경에 대한 필수 지적을 해결하고 재검증했다.
- [ ] 테스트 결과와 실제 실행 범위가 명확하다.
- [ ] 작성자 외 팀원의 리뷰를 확인했다.
- [ ] main으로 병합할 범위와 되돌릴 방법을 이해했다.
